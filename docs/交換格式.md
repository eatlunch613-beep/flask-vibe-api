# 個人記帳本前端資料交換格式規範書 (API Exchange Format)

本文件依據《專案 - 個人記帳本》步驟 14 所規範之介面標準撰寫，作為前後端分離開發時的唯一資料交換契約。前端工程師開發介面與串接 API 時，以此文件定義之外層結構、欄位命名、資料型別與狀態碼為準，無須翻閱後端路由原始碼。

---

## 壹、共通規則

全系統所有 HTTP 請求與回應均遵守以下最高原則：

### 1. 固定外層三個鍵 (Envelope Structure)
所有端點（包含成功與錯誤）之回應本體一律為 JSON 物件，且保證具備以下三個最外層鍵：
- `code` (`integer`): HTTP 狀態碼對應數字（如 `200`, `201`, `400`, `404`, `500`）。
- `message` (`string`): 繁體中文人話訊息，簡明說明操作結果或錯誤成因，不揭露底層資料庫或程式細節。
- `data` (`object` | `array` | `null`): 
  - 成功時承載實際業務資料（單筆為物件，清單為陣列）。
  - 查詢結果為空清單時，`data` 為空陣列 `[]`，狀態碼仍為 `200 OK`。
  - 當發生任何錯誤（狀態碼非 2xx）時，`data` **一律固定為 `null`**。

### 2. HTTP 狀態碼對應語義
- `200 OK`: 查詢成功、清單取得成功（含無資料之空清單 `[]`）、修改更新成功（PATCH）、作廢成功。
- `201 Created`: 資源建立成功（POST 新增成功）。
- `400 Bad Request`: 請求資料未通過商業邏輯約束或欄位格式檢驗（例如名稱重複、數值小於等於 0、兩欄位同時為空、外鍵指向不存在的實體等）。
- `404 Not Found`: 請求之 URL 路徑不存在，或指定之單筆資源 ID 於資料庫中不存在。固定錯誤訊息為：`"找不到這一筆"`。
- `500 Internal Server Error`: 伺服器內部發生未預期錯誤或資料庫連線失敗。

### 3. 客戶端不傳送的系統欄位
在發送建立（POST）或更新（PATCH）請求時，客戶端**嚴禁且不應傳送**以下欄位：
- `id`: 由資料庫自動產生的 64 位元代理整數主鍵。
- `created_at`: 資料列插入時由資料庫預設填入之 UTC 時間。
- `updated_at`: 資料列異動時由後端系統內部維護。

### 4. 日期、時間與數值型別標準
- **純日期 (`Date`)**: 採用 ISO 8601 純日期字串，格式為 `YYYY-MM-DD`（如 `2026-08-20`）。
- **時間戳記 (`Timestamptz`)**: 採用 ISO 8601 帶 UTC 時區之標準字串，格式為 `YYYY-MM-DDTHH:MM:SS+00:00`。
- **交易金額 (`Amount / Numeric`)**: 具小數精度的十進位數值（在 JSON 中以數字 `number` 呈現，如 `70.0`），嚴禁浮點精度失真。
- **匯率 (`fx_rate_to_twd`)**: 換算成新台幣之匯率（小數精度數字 `number`，台幣固定為 `1.0`，外幣大於 `0`）。

### 5. 可空欄位之表現形式
- 可空欄位在資料庫無值時，於回應 JSON 中**一律明確以 `null` 出現**，絕不省略該鍵。
- 客戶端在發送 POST 或 PATCH 請求時，傳入 JSON 的 `null` 與直接省略該欄位等價。

## 貳、資源交換格式與欄位規格

> 註：以下所有範例之 `id` 均由數字 `1` 起算示範，實際執行以伺服器回應之真實主鍵為準。

---

### 一、帳戶模組 (`accounts`)

#### 1. 成功範例（現金錢包）
- **端點**：`POST /api/accounts` 或 `GET /api/accounts/1`
- **回應本體**：
```json
{
  "code": 201,
  "message": "帳戶建立成功",
  "data": {
    "id": 1,
    "name": "現金錢包",
    "kind": "cash",
    "currency": "TWD",
    "opening_balance": 1000.0,
    "statement_day": null,
    "payment_day": null,
    "created_at": "2026-08-01T00:00:00+00:00",
    "updated_at": "2026-08-01T00:00:00+00:00"
  }
}
```

#### 2. 欄位定義表
| 欄位名稱 | 型別 | 必填 | 可空 | 說明與約束 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | integer | 系統 | 否 | 代理整數主鍵 |
| `name` | string | 是 | 否 | 帳戶名稱，全局唯一不可重複 |
| `kind` | string | 是 | 否 | 帳戶種類：`cash`, `bank`, `credit_card`, `broker` |
| `currency` | string | 否 | 否 | ISO 4217 三碼幣別，未傳送時預設為 `TWD` |
| `opening_balance` | number | 否 | 否 | 起始基底餘額，未傳送時預設為 `0.0` |
| `statement_day` | integer | 否 | 是 | 信用卡結帳日（有值時介於 1 到 31） |
| `payment_day` | integer | 否 | 是 | 信用卡繳款日（有值時介於 1 到 31） |
| `created_at` | string | 系統 | 否 | 建立時間戳記 (ISO 8601 UTC) |
| `updated_at` | string | 系統 | 否 | 最後更新時間戳記 (ISO 8601 UTC) |

## 參、錯誤回應格式

發生錯誤時，`data` 保證為 `null`，`code` 對應 HTTP 狀態碼，`message` 採用固定人話句子。

### 1. 400 Bad Request（資料格式或業務約束失敗）
當請求缺少必填項目、金額匯率小於等於 0、名稱重複、超賣股票或外鍵關聯不存在時回傳：
```json
{
  "code": 400,
  "message": "請求資料未符合約束條件或格式錯誤",
  "data": null
}
```

### 2. 404 Not Found（資源不存在）
當指定的資源 ID 不存在或查無資料時回傳：
```json
{
  "code": 404,
  "message": "找不到這一筆",
  "data": null
}
```

## 肆、內部錯誤 (Internal Errors)

本節所定義之日誌結構與內部錯誤代碼，**僅供伺服器端內部 logger 輸出與除錯追蹤使用，絕對不出現在回傳給客戶端的回應 JSON 中**。

### 1. 伺服器內部日誌物件之標準鍵 (Log Object Keys)
後端在捕獲異常或約束失敗時，必須在日誌中輸出具備以下鍵的結構化 JSON 物件：
- `timestamp`: 錯誤發生的 UTC 時間（ISO 8601 格式）。
- `level`: 日誌嚴重等級（通常為 `WARNING` 或 `ERROR`）。
- `error_code`: 系統內部標準錯誤代碼（見下方對照表）。
- `message`: 內部技術說明訊息。
- `details`: 包含除錯資訊的鍵值物件（包含 `table`, `constraint`, `sqlstate`, `field`, `value`, `path`, `request_id` 等）。

### 2. `error_code` 對照表
| 內部錯誤代碼 (`error_code`) | 說明 | 觸發原因 |
| :--- | :--- | :--- |
| `conflict.unique_name` | 唯一名稱衝突 | 分類或帳戶名稱重複（違反 `UNIQUE` 約束） |
| `conflict.unique_number` | 發票號碼衝突 | 發票號碼重複（違反 `UNIQUE (number)`） |
| `conflict.unique_symbol` | 標的代號衝突 | 同一市場下的標的代號重複（違反 `UNIQUE (market, symbol)`） |
| `validation.required` | 必填欄位遺漏 | 缺少必填參數或傳入空白字串 |
| `validation.range` | 數值範圍無效 | 金額或匯率小於等於 0、信用卡日期超出 1~31 |
| `validation.format` | 格式校驗失敗 | 幣別非 3 碼大寫、發票號非 2 碼英文加 8 碼數字、月份非 YYYY-MM |
| `validation.both_empty` | 雙欄位同時為空 | `source` 與 `note` 或 `merchant` 與 `note` 皆為空值 |
| `validation.oversold` | 庫存超賣異常 | 賣出或減資股數大於當前時序重播累計股數 |
| `foreign_key.not_found` | 外鍵目標不存在 | 指向不存在的帳戶、分類、發票或標的 |
| `foreign_key.restrict` | 關聯拒絕刪除 | 父列被參照時強制拒絕刪除操作 |
| `not_found` | 實體查無資料 | 查詢單筆資源 ID 找不到資料列 |
| `database.connection_error` | 資料庫連線異常 | 無法連線至 PostgreSQL 或連線超時 |

### 3. `conflict.unique_name` 日誌範例
當客戶端嘗試建立重複名稱的分類時，伺服器內部日誌輸出範例：
```json
{
  "timestamp": "2026-11-14T07:12:34.567Z",
  "level": "ERROR",
  "error_code": "conflict.unique_name",
  "message": "分類名稱重複，違反唯一約束",
  "details": {
    "table": "income_categories",
    "constraint": "income_categories_name_key",
    "field": "name",
    "value": "薪水",
    "sqlstate": "23505",
    "path": "/api/income-categories",
    "request_id": "req-98f3b21c-4b52-4e92-91d7"
  }
}
```

## 陸、與現況的差異

本節依據目前專案程式碼之實作現狀與講義「步驟 14」的約定，逐條列出差異對照（依約束條件不修改現行程式碼）：

| 端點 / 情境 | 目前程式現況 (Current Implementation) | 步驟 14 之約定 (Step 14 Specification) | 差異說明與前端注意事項 |
| :--- | :--- | :--- | :--- |
| `POST /api/accounts` | 回傳 HTTP `200 OK`，`code: 200` | 約定資源建立成功一律回傳 HTTP `201 Created`，`code: 201` | 前端判斷帳戶建立時建議寬容接受狀態碼 `200` 或 `201`（其他資源如入帳、花費、發票現況均已回傳 201）。 |
| 建立成功之 `message` | 各端點自訂人話字串（例如 `"帳戶建立成功"`、`"入帳建立成功"`、`"花費建立成功"`） | 步驟 14 統一通用字串 `"建立成功"` | 訊息皆為人話說明，前端應直接顯示 `message` 內容，不應依賴字串進行邏輯判斷。 |
| 400 驗證錯誤之 `message` | 會明確指稱問題欄位（例如 `"入帳金額必須大於 0"`、`"分類名稱已存在"`） | 步驟 14 統一收斂為分類代碼映射後的標準人話說明 | 現行後端提供更具體之欄位錯誤指引，可直接作為表單驗證提示字串顯示給使用者。 |
