# 個人記帳本前端串接技術規格書 (Frontend Integration Specification)

本文件依據 `./docs/交換格式.md`（API 資料交換契約）與 `./docs/資料表設計.md`（Supabase PostgreSQL 資料表設計）進行專案工程分析，專為後續手機端畫面（Mobile Web / PWA / Native App）開發所制定之前端串接技術規格書。

前端開發工程師在進行畫面設計、狀態管理、表單驗證與 API 串接時，以此文件定義之外層結構、欄位命名、資料型別、狀態碼與錯誤處理原則為準。

---

## 壹、共通規則 (Common Rules)

全系統所有 HTTP 請求與回應均遵守以下最高原則：

### 1. 固定外層三個鍵 (Envelope Structure)
所有 API 端點（無論成功或失敗）之回應本體一律為標準 JSON 物件，且保證具備以下三個最外層鍵：
- `code` (`integer`): 與 HTTP 狀態碼相同之整數（如 `200`, `201`, `400`, `404`, `500`）。
- `message` (`string`): 繁體中文人話訊息，說明業務執行結果或錯誤原因，適合直接作為 UI 提示訊息，絕不揭露底層資料庫或程式碼技術細節。
- `data` (`object` | `array` | `null`): 
  - 成功查詢單筆資源時，`data` 為該資源的 JSON 物件。
  - 成功查詢清單資源時，`data` 為陣列。若查無資料或為空清單，`data` 固定為空陣列 `[]`，狀態碼仍為 `200 OK`。
  - **當發生任何錯誤（HTTP 狀態碼非 2xx）時，`data` 一律固定為 `null`**。

### 2. HTTP 狀態碼語義與處理
- `200 OK`: 查詢成功、清單取得成功（含空清單 `[]`）、更新成功（PATCH）、作廢成功。
- `201 Created`: 資源建立成功（POST 新增成功）。
- `400 Bad Request`: 客戶端傳送之請求未通過欄位格式檢驗或商業邏輯約束（如必填欄位空白、名稱重複、金額小於等於 0、外鍵關聯不存在、股票超賣等）。
- `404 Not Found`: 請求之 URL 路徑不存在，或指定之單筆資源 ID 於資料庫中不存在。固定人話訊息為：`"找不到這一筆"`。
- `500 Internal Server Error`: 伺服器內部發生未預期錯誤或資料庫連線失敗。

### 3. 客戶端嚴格不傳送的系統欄位
在發送建立（`POST`）或更新（`PATCH`）請求的 JSON Payload 時，客戶端**嚴格禁止傳送**以下由系統與資料庫維護的欄位：
- `id`: 由資料庫自動產生的 64 位元代理整數主鍵。
- `created_at`: 資料列建立時由資料庫預設填入之 UTC 時間戳記。
- `updated_at`: 資料列變更時由後端系統內部維護之 UTC 時間戳記。

### 4. 日期、時間戳記與數值型別標準
- **純日期 (`Date`)**: 採用 ISO 8601 純日期字串，格式固定為 `YYYY-MM-DD`（如 `2026-08-20`）。
- **時間戳記 (`Timestamptz`)**: 採用 ISO 8601 帶 UTC 時區之標準字串，格式為 `YYYY-MM-DDTHH:MM:SS+00:00`。
- **交易金額與數值 (`Amount / Numeric`)**: 具小數精度的十進位數值，在 JSON 中一律以**數字 (`number`)** 呈現（如 `70.0`, `1000.0`），嚴禁轉為純字串，且前端計算時應注意避免 JavaScript 浮點數精度誤差。
- **匯率 (`fx_rate_to_twd`)**: 換算成新台幣之匯率（小數精度數字 `number`，台幣固定為 `1.0`，外幣大於 `0`）。

### 5. 可空欄位之表現形式
- 可空欄位在資料庫無值時，於回應 JSON 中**一律明確以 `null` 出現**，絕不省略該鍵。
- 客戶端在發送 `POST` 或 `PATCH` 請求時，傳入 JSON 的 `null` 與直接省略該鍵具等價效果。

## 貳、錯誤句子與異常處理表 (Error Handling)

發生錯誤時，HTTP 狀態碼為對應之 4xx/5xx，回應之 `data` 保證為 `null`，`message` 採用固定人話句子。

### 1. 錯誤代碼 (`error_code`) 與客戶端提示句子對照表

| 內部錯誤代碼 (`error_code`) | HTTP 狀態碼 | 客戶端人話句子 (`message`) | 觸發原因說明 |
| :--- | :--- | :--- | :--- |
| `conflict.unique_name` | 400 | 分類名稱已存在 / 帳戶名稱已存在 | 分類或帳戶名稱重複（違反唯一約束） |
| `conflict.unique_number` | 400 | 發票號碼已存在 | 發票號碼重複（違反發票號碼唯一約束） |
| `conflict.unique_symbol` | 400 | 此市場下標的代號已存在 | 同一市場下的投資標的代號重複 |
| `validation.required` | 400 | 必填欄位不可為空 | 缺少必填參數或傳入空白字串 |
| `validation.range` | 400 | 金額或數值範圍無效 | 金額或匯率小於等於 0、信用卡結帳繳款日超出 1~31 |
| `validation.format` | 400 | 資料格式錯誤 | 幣別非 3 碼大寫、發票號非 2 碼英文加 8 碼數字、月份非 YYYY-MM |
| `validation.both_empty` | 400 | 來源與備註不可同時為空 | `source` 與 `note` 皆為空值（花費時為 `merchant` 與 `note`） |
| `validation.oversold` | 400 | 庫存不足，不得超賣 | 賣出或減資股數大於目前時序重播累計之持有股數 |
| `foreign_key.not_found` | 400 | 所參照的關聯資料不存在 | 指向不存在的帳戶、分類、發票或投資標的 |
| `foreign_key.restrict` | 400 | 該項目已被其他紀錄引用，無法刪除 | 父資料列被子資料列參照，依外鍵保護拒絕刪除 |
| `not_found` | 404 | 找不到這一筆 | 查詢單筆資源 ID 於資料庫中不存在 |
| `database.connection_error` | 500 | 資料庫連線異常，請稍後再試 | 無法連線至資料庫或連線超時 |
| `upstream.twse` | 500 | 證交所目前沒有回應 | 外部台灣證券交易所報價伺服器逾時或連線失敗（註：交換格式現況未包含此代碼與報價端點，此為預留規格） |

### 2. 資料庫技術細節隔離原則
- **表名 (`table`)、約束名 (`constraint`)、SQLSTATE 代碼、原始 SQL 查詢語法、程式堆疊（Stack Trace）嚴禁出現在回傳給前端客戶端的 JSON 中**。
- 上述技術資訊僅限於伺服器端內部 logger 輸出供後端工程師除錯；前端介面只需判斷 `code` 並將繁體中文人話 `message` 顯示於 UI Toast 或表單提示列。

### 一、帳戶模組 (`accounts`)

#### 1. 建立帳戶
- **方法與路徑**：`POST /api/accounts`
- **查詢參數**：無
- **請求欄位**：
  - `name` (`string`, 必填): 帳戶名稱，不可重複。
  - `kind` (`string`, 必填): 帳戶種類：`cash`（現金）、`bank`（銀行）、`credit_card`（信用卡）、`broker`（證券交割戶）。
  - `currency` (`string`, 選填): ISO 4217 3 碼幣別，未傳送時預設為 `TWD`。
  - `opening_balance` (`number`, 選填): 起始基底餘額，未傳送時預設為 `0.0`。
  - `statement_day` (`integer`, 選填, 可空): 信用卡結帳日（1 至 31），非信用卡為 `null`。
  - `payment_day` (`integer`, 選填, 可空): 信用卡繳款日（1 至 31），非信用卡為 `null`。
- **成功時 `data` 欄位**：
  `id`, `name`, `kind`, `currency`, `opening_balance`, `statement_day`, `payment_day`, `created_at`, `updated_at`。
- **最小 JSON 範例**：
  - 請求：
    ```json
    {
      "name": "現金錢包",
      "kind": "cash"
    }
    ```
  - 回應 (`201 Created` / 現況程式相容 `200 OK`)：
    ```json
    {
      "code": 201,
      "message": "帳戶建立成功",
      "data": {
        "id": 1,
        "name": "現金錢包",
        "kind": "cash",
        "currency": "TWD",
        "opening_balance": 0.0,
        "statement_day": null,
        "payment_day": null,
        "created_at": "2026-08-01T00:00:00+00:00",
        "updated_at": "2026-08-01T00:00:00+00:00"
      }
    }
    ```

#### 2. 取得單筆帳戶
- **方法與路徑**：`GET /api/accounts/{id}`
- **查詢參數**：無
- **請求欄位**：無
- **成功時 `data` 欄位**：同建立帳戶。
- **最小 JSON 範例**：
  - 回應 (`200 OK`)：
    ```json
    {
      "code": 200,
      "message": "取得成功",
      "data": {
        "id": 1,
        "name": "現金錢包",
        "kind": "cash",
        "currency": "TWD",
        "opening_balance": 1000.0,
        "statement_day": null,
        "payment_day": null,
        "created_at": "2026-08-01T00:00:00+00:00",
        "updated_at": "2026-08-01T00:00:00+00:00"
      }
    }
    ```

#### 3. 取得帳戶清單
- **方法與路徑**：`GET /api/accounts`
- **查詢參數**：無
- **請求欄位**：無
- **成功時 `data` 欄位**：帳戶物件陣列。
- **最小 JSON 範例**：
  - 回應 (`200 OK`)：
    ```json
    {
      "code": 200,
      "message": "取得成功",
      "data": [
        {
          "id": 1,
          "name": "現金錢包",
          "kind": "cash",
          "currency": "TWD",
          "opening_balance": 1000.0,
          "statement_day": null,
          "payment_day": null,
          "created_at": "2026-08-01T00:00:00+00:00",
          "updated_at": "2026-08-01T00:00:00+00:00"
        }
      ]
    }
    ```

### 二、帳戶餘額查詢 (`accounts/balance`)

#### 1. 取得指定帳戶餘額
- **方法與路徑**：`GET /api/accounts/{id}/balance`
- **查詢參數**：無
- **請求欄位**：無
- **成功時 `data` 欄位**：
  - `account_id` (`integer`): 帳戶 ID。
  - `balance` (`number`): 當前動態計算之原幣累計餘額。
  - `twd_balance` (`number`): 折合新台幣後之總餘額。
- **最小 JSON 範例**：
  - 回應 (`200 OK`)：
    ```json
    {
      "code": 200,
      "message": "成功取得帳戶餘額",
      "data": {
        "account_id": 1,
        "balance": 800.0,
        "twd_balance": 800.0
      }
    }
    ```

### 三、帳戶移轉模組 (`transfers`)

#### 1. 建立轉帳
- **方法與路徑**：`POST /api/transfers`
- **查詢參數**：無
- **請求欄位**：
  - `transferred_on` (`string`, 必填): 轉帳日期 (`YYYY-MM-DD`)。
  - `amount` (`number`, 必填): 轉出金額，必須大於 0。
  - `currency` (`string`, 必填): 幣別代碼（3 碼大寫）。
  - `fx_rate_to_twd` (`number`, 必填): 換算台幣匯率，必須大於 0。
  - `from_account_id` (`integer`, 必填): 轉出帳戶 ID。
  - `to_account_id` (`integer`, 必填): 轉入帳戶 ID，不可與轉出帳戶相同。
  - `note` (`string`, 選填, 可空): 備註說明。
- **成功時 `data` 欄位**：
  `id`, `transferred_on`, `amount`, `currency`, `fx_rate_to_twd`, `from_account_id`, `to_account_id`, `note`, `created_at`, `updated_at`。
- **最小 JSON 範例**：
  - 請求：
    ```json
    {
      "transferred_on": "2026-08-15",
      "amount": 200.0,
      "currency": "TWD",
      "fx_rate_to_twd": 1.0,
      "from_account_id": 1,
      "to_account_id": 2
    }
    ```
  - 回應 (`201 Created`)：
    ```json
    {
      "code": 201,
      "message": "轉帳建立成功",
      "data": {
        "id": 1,
        "transferred_on": "2026-08-15",
        "amount": 200.0,
        "currency": "TWD",
        "fx_rate_to_twd": 1.0,
        "from_account_id": 1,
        "to_account_id": 2,
        "note": null,
        "created_at": "2026-08-15T10:00:00+00:00",
        "updated_at": "2026-08-15T10:00:00+00:00"
      }
    }
    ```

## 伍、兩份文件的差異（交換格式 vs 資料表設計）

本節逐條比對 `./docs/交換格式.md`（以下簡稱【交換格式】）與 `./docs/資料表設計.md`（以下簡稱【資料表設計】）之間在實體名稱、欄位命名、可空性與業務約束上的不一致之處。前端串接時以【交換格式】之外層與欄位名稱為準，並參考此對照表理解底層約束邊界：

### 1. 帳戶模組 (`accounts` vs `account`)
- **實體與表名**：【交換格式】使用複數 `accounts`，【資料表設計】使用單數 `account`。
- **帳戶種類欄位**：
  - 【交換格式】欄位名為 `kind`，可選值為 `cash`, `bank`, `credit_card`, `broker`。
  - 【資料表設計】欄位名為 `account_type`，可選值為 `cash`, `bank`, `credit_card`, `brokerage_settlement`（證券戶命名不同）。
- **起始基底餘額欄位**：
  - 【交換格式】欄位名為 `opening_balance`。
  - 【資料表設計】欄位名為 `initial_balance`。
- **信用卡結帳日與繳款日 (`statement_day`, `payment_day`)**：
  - 【交換格式】定義了 `statement_day` 與 `payment_day`（可為 `null`，整數 1~31）。
  - 【資料表設計】的 `account` 表中完全沒有這兩個欄位。
- **帳戶啟用狀態 (`is_active`)**：
  - 【交換格式】未包含 `is_active` 欄位（請求與回應皆無）。
  - 【資料表設計】包含 `is_active` (`BOOLEAN NOT NULL DEFAULT true`)。
- **備註欄位 (`note`)**：
  - 【交換格式】在帳戶模組無 `note` 欄位。
  - 【資料表設計】包含可空之 `note` (`TEXT`)。

### 2. 帳戶移轉模組 (`transfers` vs `account_transfer`)
- **實體與表名**：【交換格式】為 `transfers`，【資料表設計】為 `account_transfer`。
- **轉帳日期時間**：
  - 【交換格式】為純日期 `transferred_on` (`YYYY-MM-DD`)。
  - 【資料表設計】為時間戳記 `transfer_date` (`TIMESTAMPTZ`)。
- **轉帳金額與手續費**：
  - 【交換格式】僅有單一 `amount`（轉出金額），無手續費欄位。
  - 【資料表設計】拆為 `out_amount`（轉出金額）、`in_amount`（轉入金額）與 `fee_amount`（手續費）。
- **匯率欄位命名**：
  - 【交換格式】使用 `fx_rate_to_twd`。
  - 【資料表設計】使用 `exchange_rate_to_twd`。

### 3. 入帳明細模組 (`incomes` vs `income`)
- **實體與表名**：【交換格式】為 `incomes`，【資料表設計】為 `income`。
- **入帳日期時間**：
  - 【交換格式】為純日期 `received_on` (`YYYY-MM-DD`)。
  - 【資料表設計】為時間戳記 `income_date` (`TIMESTAMPTZ`)。
- **金額欄位與台幣折算**：
  - 【交換格式】僅有原幣金額 `amount`。
  - 【資料表設計】包含原幣 `original_amount` 與資料表實體儲存之折合台幣金額 `twd_amount`。
- **匯率欄位命名**：
  - 【交換格式】為 `fx_rate_to_twd`。
  - 【資料表設計】為 `exchange_rate_to_twd`。
- **關聯投資交易外鍵**：
  - 【交換格式】欄位名為 `trade_id`。
  - 【資料表設計】欄位名為 `investment_transaction_id`。
- **來源與備註之防空約束**：
  - 【交換格式】業務規則明確規定 `source` 與 `note` 不可同時為空（`validation.both_empty`）。
  - 【資料表設計】在資料庫 DDL 中未設計 CHECK 約束，皆為普通可空欄位，屬 API 層檢驗。
- **發票與投資互斥約束**：
  - 【資料表設計】具備 CHECK 約束 `chk_income_exclusive_source`，強制 `invoice_id` 與 `investment_transaction_id` 不能同時存在。
  - 【交換格式】欄位說明分別標示唯一不可重複綁定，未在格式層面直觀揭示兩者完全互斥。

### 4. 花費明細模組 (`expenses` vs `expense`)
- **實體與表名**：【交換格式】為 `expenses`，【資料表設計】為 `expense`。
- **消費日期與結算日**：
  - 【交換格式】為純日期 `spent_on` (`YYYY-MM-DD`) 與 `settled_on` (`YYYY-MM-DD`, 可空)。
  - 【資料表設計】為時間戳記 `expense_date` (`TIMESTAMPTZ`) 與 `settlement_date` (`TIMESTAMPTZ`, 可空)。
- **金額欄位**：
  - 【交換格式】僅有原幣金額 `amount`。
  - 【資料表設計】包含 `original_amount` 與折合台幣 `twd_amount`。
- **匯率欄位命名**：
  - 【交換格式】為 `fx_rate_to_twd`。
  - 【資料表設計】為 `exchange_rate_to_twd`。
- **商家名稱欄位**：
  - 【交換格式】欄位名為 `merchant`。
  - 【資料表設計】欄位名為 `merchant_name`。
- **商家與備註之防空約束**：
  - 【交換格式】規定 `merchant` 與 `note` 不可同時為空（`validation.both_empty`）。
  - 【資料表設計】在資料庫 DDL 中無此 CHECK 約束。

### 5. 統一發票模組 (`invoices` vs `invoice`)
- **實體與表名**：【交換格式】為 `invoices`，【資料表設計】為 `invoice`。
- **發票號碼與唯一性約束**：
  - 【交換格式】欄位名為 `number`，約束為全局唯一（`UNIQUE (number)`，觸發 `conflict.unique_number`）。
  - 【資料表設計】欄位名為 `invoice_number`，約束為與期別複合之唯一（`UNIQUE (period, invoice_number)`）。
- **開立日期時間**：
  - 【交換格式】為純日期 `issued_on` (`YYYY-MM-DD`)。
  - 【資料表設計】為時間戳記 `invoice_date` (`TIMESTAMPTZ`)。
- **發票總額**：
  - 【交換格式】為 `amount`（必須大於 0）。
  - 【資料表設計】為 `total_amount`（大於等於 0，CHECK `total_amount >= 0`）。
- **種類、幣別與匯率 (`kind`, `currency`, `fx_rate_to_twd`)**：
  - 【交換格式】包含 `kind` (`paper` / `electronic`)、`currency` 與 `fx_rate_to_twd`。
  - 【資料表設計】完全沒有此三項欄位，預設視為新台幣。
- **期別欄位命名**：
  - 【交換格式】欄位名為 `period_key`（如 `2026-07`）。
  - 【資料表設計】欄位名為 `period`（如 `2026-07`）。
- **統一編號欄位**：
  - 【交換格式】賣方統編名為 `seller_ban`，無買方統編。
  - 【資料表設計】賣方統編名為 `seller_tax_id`，且額外支援買方統編 `buyer_tax_id`。
- **對獎狀態與中獎關聯**：
  - 【交換格式】包含字串狀態 `prize_status`（`unchecked`, `lost`, `won`, `claimed`, `void`）。
  - 【資料表設計】無字串狀態列舉，而是直接儲存外鍵 `winning_prize_id` 指向 `invoice_prize_rule(id)`。
- **關聯花費與品項列表**：
  - 【交換格式】在取得發票時附帶 `expense_ids` 陣列與 `items` 陣列。
  - 【資料表設計】為標準 1NF 關聯模型，父表不直接紀錄子表 ID 陣列。

### 6. 發票品項模組 (`invoice_items` vs `invoice_item`)
- **品項名稱**：
  - 【交換格式】欄位名為 `name`。
  - 【資料表設計】欄位名為 `item_name`。
- **小計金額**：
  - 【交換格式】欄位名為 `line_amount`。
  - 【資料表設計】欄位名為 `amount`。
- **品項備註 (`note`)**：
  - 【交換格式】未包含 `note`。
  - 【資料表設計】包含可空之 `note` (`TEXT`)。

### 7. 開獎期別與獎項模組 (`draw-periods` & `draw-prizes` vs `invoice_lottery_draw` & `invoice_prize_rule`)
- **領域模型設計**：
  - 【交換格式】以期別為路徑層級（`POST /api/draw-periods/{id}/prizes`），獎項屬性包含 `tier`, `matching_number`, `amount`。
  - 【資料表設計】採高度正規化，拆解為 `invoice_prize_rule`（獎項規則表，含 `prize_code`, `prize_name`, `prize_amount`, `match_type`）與 `invoice_lottery_draw`（各期開出獎號表，含 `period`, `prize_rule_id`, `winning_number`, `draw_date`）。
- **開獎期別端點**：
  - 【交換格式】未定義期別主檔之新增與查詢端點。

### 8. 投資標的模組 (`instruments` vs `investment_asset`)
- **實體與表名**：【交換格式】為 `instruments`，【資料表設計】為 `investment_asset`。
- **市場類別代碼 (`market`)**：
  - 【交換格式】為小寫字串：`tw_stock`, `us_stock`, `fund`, `other`。
  - 【資料表設計】為大寫字串：`TW`, `US`, `CRYPTO`, `OTHER`。
- **備註欄位 (`note`)**：
  - 【交換格式】未定義 `note` 欄位。
  - 【資料表設計】包含可空之 `note` (`TEXT`)。

### 9. 投資交易模組 (`trades` vs `investment_transaction`)
- **實體與表名**：【交換格式】為 `trades`，【資料表設計】為 `investment_transaction`。
- **外鍵欄位命名**：
  - 【交換格式】標的為 `instrument_id`（必填）、交割帳戶為 `account_id`（必填）。
  - 【資料表設計】標的為 `asset_id`（必填）、交割帳戶為 `settlement_account_id`（可空，因分割/合併/配股無現金流）。
- **交易型態命名 (`trade_type` vs `transaction_type`)**：
  - 【交換格式】`drip`、`split`、`merge`。
  - 【資料表設計】`dividend_reinvestment`、`stock_split`、`stock_reverse_split`。
- **交易日期時間**：
  - 【交換格式】為純日期 `traded_on` (`YYYY-MM-DD`)。
  - 【資料表設計】為時間戳記 `transaction_date` (`TIMESTAMPTZ`)。
- **股數與金額計算屬性**：
  - 【交換格式】分開記載 `quantity`（成交股數）、`price`（單價）、`cash_amount`（現金款）、`ratio`（拆合股比率）。
  - 【資料表設計】採用淨額變動模型：`shares_delta`（淨變動量，買進為正、賣出為負）、`unit_price`、`total_cash_amount`、`split_ratio`。
- **作廢狀態戳記 (`voided_at`)**：
  - 【交換格式】包含 `voided_at`（`TIMESTAMPTZ`，可空，正常交易為 `null`），支援交易作廢。
  - 【資料表設計】完全無 `voided_at` 欄位，且在「陸、這一次不建的表」明確指出排除軟刪除欄位。
- **匯率欄位命名**：
  - 【交換格式】為 `fx_rate_to_twd`。
  - 【資料表設計】為 `exchange_rate_to_twd`。

### 10. 即時行情與報價模組 (`stock_quote`, `market_daily_price`, `twse`)
- **行情與報價功能**：
  - 【資料表設計】在第 619 行「陸、這一次不建的表」第 4 點明確規範：**即時股價與歷史行情表為這一次明確排除項目**，不抓取公開市場報價，不計算未實現損益市值，專注於交易紀錄與買入加權成本。
  - 【交換格式】全篇未提供台股報價、報價清單、單筆最新報價之端點規格與資料結構。
